# Администратор и реальные метрики — версия 1.3

В этой рабочей среде отсутствуют Supabase URL/ключи и доступ к настройкам Vercel. Настоящий админский аккаунт **не создан**. Пароль-заглушка в браузер не добавлялся. Это внешняя предпосылка, а не скрытая «успешная авторизация».

## Подключение

1. Создайте бесплатный Supabase-проект или используйте свой. Примените SQL из `supabase/migrations/202610220001_platform.sql`, затем `202610230001_release_1_3.sql` через SQL Editor. Подробности исходной схемы — в `SUPABASE.md`.
2. В настройках проекта Vercel добавьте `VITE_SUPABASE_URL` и только публичный anon/publishable key в `VITE_SUPABASE_ANON_KEY`. Пересоберите сайт. Настройте Site URL/callback в Supabase Auth.
3. На доверенном компьютере создайте игнорируемый `.env.admin`:

```dotenv
SUPABASE_URL=https://ваш-проект.supabase.co
SUPABASE_SERVICE_ROLE_KEY=секретный-серверный-ключ
# Необязательно: действующая почта для восстановления доступа.
# Без неё будет создан случайный логин на зарезервированном домене .invalid.
ADMIN_EMAIL=ваша-почта
```

Service-role key нельзя помещать в `VITE_*`, исходники, чат или frontend. `.env.admin` и `.private/` исключены из Git.

4. Выполните `npm run admin:create`. Команда создаст отдельного пользователя через настоящий Admin API, назначит серверную роль и запишет случайные логин/пароль в `.private/admin-*.json` с правами 0600. Она не печатает пароль в журнал. Если назначение роли не удалось, откатывает только что созданный аккаунт. Скопируйте пароль в менеджер паролей; не публикуйте файл.
5. Войдите на `/account`, затем откройте `/admin`. Роль запрашивается через серверный `is_admin`; `role=admin` в localStorage ничего не даёт. Из админки можно читать реальные записи и менять роли через защищённый журналируемый RPC. Снять собственный административный доступ нельзя.

## Реальная аналитика

В версии 1.3 приложение после согласия пользователя передаёт минимальные учебные события в настроенный Supabase. Анонимному гостю назначается случайный actor ID, не имя/почта. Хранятся тип события, время, сессия, устройство, категория источника и ограниченные параметры. Заметки, пароли, email и реквизиты не передаются.

`collect_product_event` валидирует схему на сервере, не разрешает произвольные поля, ограничивает частоту, дедуплицирует по UUID события. Офлайн-события остаются локально и повторяются при восстановлении связи. Без подключения отправки нет. Отключение согласия прекращает доставку и удаляет локальную очередь/события; уже полученные сервером записи не удаляются автоматически.

Админка читает реальные серверные записи. Перед загрузкой она не показывает «нулевые» или синтетические метрики. Пустая серверная выборка и отсутствие подключения различаются. Средние баллы из событий — клиентские учебные сообщения, а не подтверждённое RPC-оценивание; пользовательские события не следует использовать как антифрод-доказательство. Анонимные идентификаторы оценивают активность устройств/браузеров, а не точное число людей.

Чтобы появились общие показатели, недостаточно одной миграции: нужны действующее подключение, публикация новой сборки, согласие посетителей и реальные действия на сайте. Старые посещения восстановить задним числом нельзя.

Серверный рейтинг принимает только проверенные серверные попытки. Клиентское обучение пока использует локальный прогресс; интеграция миссий с серверным оцениванием и серверный контент остаются отдельным следующим шагом, описанным в SUPABASE.md. Поэтому отсутствие участников в реальном рейтинге сейчас честнее вымышленных строк.

## Порядок обучения и сохранность

Кейсы на сервере получают поле `position`; при последующей публикации материалов указывайте порядковый номер 1–9. RPC `start_attempt` проверяет предыдущее завершение для обычного пользователя; администратору доступен свободный порядок. Старые серверные и локальные попытки сохраняют доступ.

В гостевом режиме дорожка использует локальный прогресс. Он не является серверным правом доступа или подтверждением честности баллов. Завершение на любой балл открывает следующий шаг; повторение остаётся доступным, более новые результаты не стираются импортом старой резервной копии.

## Что проверено

Проверены клиентские сценарии, валидация/доставка событий в mock, правила порядка и отказ без настоящей роли. Команда создания аккаунта протестирована на mock-ответах, включая откат. Реальный Admin API и миграция не выполнены без подключения. Парсерные/структурные проверки SQL не заменяют проверку RLS на реальном проекте.
