# Подключение Supabase к Product Lab 2.0

Интеграция подготовлена, но **не является подключённой базой данных**. При отсутствии конфигурации приложение работает в гостевом режиме. Гостевые оценки, достижения, сертификаты и демонстрационные рейтинги не являются проверенными сервером результатами.

## 1. Проект и публичная конфигурация

1. Создайте проект Supabase на подходящем бесплатном тарифе и выберите регион хранения. До подключения реальных пользователей проверьте условия сервиса и применимые правила приватности.
2. В SQL Editor выполните по порядку `supabase/migrations/202610220001_platform.sql`, `202610230001_release_1_3.sql` и `202610240001_product_lab_3.sql` (3.0: решения 0–3 с «Ограниченным пилотом», причины 0–6, порядок 13 миссий). Повторное применение начальной миграции к существующим таблицам не предусмотрено: последующие изменения оформляйте новыми миграциями, без удаления данных.
3. В Authentication → URL Configuration задайте Site URL и разрешённые Redirect URLs для production и выбранного Vercel Preview. Не используйте произвольный `*` для незнакомых доменов.
4. В Authentication → Providers включите Email, подтверждение почты и политику пароля не короче 10 символов. Для массовых писем потребуется собственная почтовая инфраструктура; бесплатные лимиты Supabase могут ограничивать тестовые письма.
5. В Vercel задайте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, затем пересоберите Preview. Для локальной проверки задайте их в отдельном `.env.local`, исключённом из Git.

Используйте **publishable/anon key**. Он публичен и не является серверным секретом. Клиент отклоняет ключи `service_role` и `sb_secret_*`. Никогда не помещайте service key в Vite: переменные `VITE_*` встраиваются в браузерный bundle. RLS защищает таблицы независимо от того, известен ли клиентский anon key.

Проверьте фактическую регистрацию, подтверждение почты, вход, выход и восстановление пароля. Без этой проверки нельзя заявлять, что облачный режим работает. Пароли отправляются только в настроенный Supabase Auth и не записываются в аналитику. Сессия хранится в `sessionStorage` браузера, при запрете хранилища — в памяти. Refresh token — чувствительный auth-артефакт: защитите сайт HTTPS и от XSS, не добавляйте сторонние скрипты без проверки.

## 2. Первый администратор

1. Зарегистрируйте обычного пользователя и подтвердите его почту.
2. В доверенном Supabase Dashboard → Authentication найдите UUID именно этого пользователя.
3. **Только в SQL Editor от владельца проекта** выполните:

```sql
insert into public.roles(user_id, role)
values ('ВСТАВЬТЕ-ПРОВЕРЕННЫЙ-UUID-ПОЛЬЗОВАТЕЛЯ'::uuid, 'admin')
on conflict do nothing;
```

4. Проверьте `select * from public.roles where user_id = 'UUID'::uuid;` и войдите заново.

Не назначайте роль из браузерной консоли, `user_metadata`, URL, localStorage или публичного API. Для таблицы `roles` нет клиентских политик записи и нет RPC выдачи роли. `is_admin()` читает назначение из PostgreSQL с `auth.uid()`. Обычный участник не может изменить чужой профиль или собственные права. Демо-админка лишь показывает синтетические данные и **не выдаёт права администратора**.

## 3. Модель и граница доверия

Миграция создаёт `profiles`, `roles`, `courses`, `modules`, `lessons`, `cases`, `case_variants`, `attempts`, `answers`, `skill_scores`, `achievements`, `certificates`, `analytics_events`, `content_versions`, `admin_audit_log`, а также `guest_progress` для переноса локальной истории.

- RLS включён на всех публичных таблицах.
- Личные данные доступны владельцу; административный доступ проверяется сервером.
- Из клиента разрешено изменять только псевдоним и флаг публичного рейтинга собственного профиля.
- Прямые записи клиентом в роли, баллы, попытки и сертификаты запрещены.
- Эталоны находятся в закрытой схеме `private.case_rubrics`, недоступной через REST.
- Прогресс, импортированный из браузера, хранится как **непроверенный снимок**. Он не создаёт проверенные попытки, серверные награды и сертификаты.
- Публичный рейтинг возвращает только псевдонимы и агрегаты пользователей, давших согласие. Электронная почта в результат не входит.

## 4. Публикация учебных материалов для серверного режима

Миграция не копирует автоматически клиентские учебные JSON в БД. Курс создаётся неопубликованным. Для реального серверного обучения подготовьте проверенную версию контента:

1. Создайте модули и уроки с новыми ID из 14-слайдовой программы.
2. Создайте девять кейсов (`market`, `stream`, `food`, `ads`, `interface`, `price`, `recommend`, `quality`, `final`) с `course_id='product-lab'`; `final` отметьте `final_case=true`. Обязательные миссии отметьте `required=true`.
3. Для каждого сценария создайте неизменяемую строку `case_variants`: `case_id`, `version`, `variant_index`, `scenario`. Не включайте скрытый эталон в открытый `scenario`, если он не должен быть виден студенту.
4. От имени доверенного владельца добавьте соответствующий эталон в `private.case_rubrics`. Он содержит ID диагностического узла, правильные индексы ответов, решение и массив верных причин. Поля должны точно соответствовать опубликованной версии.
5. Прогоните математику и рубрику на тестовых ответах, затем опубликуйте варианты, кейсы и курс. Не изменяйте старую версию варианта: создавайте новую. Старые попытки продолжают ссылаться на прежний вариант.

Доступные серверные операции:

- `start_attempt(variant_id)` — создаёт попытку у текущего пользователя.
- `record_hint(attempt_id, stage)` — фиксирует подсказку; повторный вызов на том же этапе не увеличивает штраф.
- `submit_attempt(attempt_id, answers)` — считает 25 + 20 + 15 + 20 + (12 + 8), вычитает 2 за каждый уникальный этап с подсказкой. Клиентский `score` не принимается. Завершённый результат неизменяем.
- `issue_certificate('product-lab')` — проверяет все обязательные миссии, финальный кейс и средний лучший балл ≥ 70; выдача идемпотентна.
- `public_leaderboard(weekly)` — сумма лучших результатов уникальных кейсов; повторы не накручивают баллы.
- `save_content_draft(...)` — сохраняет валидированный черновик от редактора и журналирует действие. Публикация намеренно требует отдельной проверки математики и рубрики.

HTTP-адаптеры находятся в `src/services/supabase.ts`. Текущее гостевое обучение не подменяется серверным автоматически. Для промышленного Connected Mode нужно связать каждый этап миссии с этими RPC и опубликованными серверными вариантами, обработать офлайн-конфликты и проверить RLS интеграционными тестами на реальном проекте. Пока это не выполнено, приложение должно продолжать честно обозначать локальные оценки и сертификаты.

## 5. Импорт локального прогресса

На странице аккаунта импорт предлагается после входа и требует нажатия кнопки. Передаётся приватный снимок версии 2, включая пользовательское обоснование. Аналитика эти тексты не получает. Сервер объединяет попытки по ID, отдаёт приоритет завершённым и более новым результатам. Локальный ключ `product-lab-v1` не удаляется. Обратная загрузка использует валидатор схемы и объединение, не стирающее локальную историю.

Импорт не является подтверждением честности клиентских баллов. `guest_progress.verified` может быть только `false`, клиентские сертификаты не импортируются в серверную выдачу.

## 6. Аналитика и приватность

Серверное `record_analytics_event` ограничивает типы событий, допустимые параметры, размер payload и частоту. Вызывайте его только после согласия пользователя. Пароли, почта, текст обоснования, платёжные данные и токены запрещены. События от анонимных гостей остаются локальными: серверный RPC требует сессию. Администратор видит данные в пределах серверной роли; демо-наборы не должны записываться в реальные таблицы.

## 7. Что проверено и что требует инфраструктуры

В репозитории есть unit-тесты проверки публичного ключа, URL, входных данных и правил допуска; структурные тесты SQL проверяют наличие RLS и запрет клиентских привилегированных записей. Это **не выполнение миграции PostgreSQL**. В текущей среде Supabase не настроен и PostgreSQL не запускался. Нужно отдельно проверить миграцию, письма Auth, SQL-функции, доступ двух разных пользователей, запрет повышения роли и все внешние настройки. После подключения добавьте ограничение хранения аналитики и резервное копирование по выбранной политике.

Дополнительно синтаксис 86 SQL-операторов проверен PostgreSQL-парсером pglast; 11 тел PL/pgSQL разобраны с заменой пользовательских составных типов на `record` только в памяти проверяющего скрипта. Это проверка синтаксиса, а не проверка миграции в Supabase или выполнения RLS/RPC. Административный адаптер считает строки через `Prefer: count=exact`; загрузка реальных событий ограничена последними 30 днями и 10 000 записей с флагом `truncated`, чтобы отчёты не выдавали усечённую выборку за полную.
